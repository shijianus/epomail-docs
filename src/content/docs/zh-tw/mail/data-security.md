# 資料處理與安全維護

**生效日期：2026 年 9 月 30 日｜版本：5.1**

本文件依[隱私權政策](/zh-tw/mail/privacy-policy/)第 10 節，說明本服務個人資料之生命週期、各類資料之處理矩陣，以及營運者為防止個人資料被竊取、竄改、毀損、滅失或洩漏所建立之安全維護措施。本文件同時作為當事人查閱及主管機關依法檢查之基礎文件。

## 1. 資料生命週期

![EpoCanvas Mail 資料生命週期：蒐集（註冊與收發信）→ 處理（邊緣節點解析與加密）→ 利用（提供服務與安全防護）→ 傳輸（受託處理者與當事人觸發之功能）→ 保存（D1/KV/R2）→ 銷毀（7 日例行清理與實體刪除），各階段對應告知事項與處理標準](/images/mail/data-flow.svg)

*圖：個人資料於本服務之生命週期。各階段之處理性質見[隱私權政策](/zh-tw/mail/privacy-policy/)第 5 節。*

## 2. 資料處理矩陣

| 資料類別 | 具體項目 | 處理目的 | 儲存媒體與安全基準 | 保存與銷毀 |
| --- | --- | --- | --- | --- |
| 帳號憑證 | 電子郵件地址、使用者名稱、密碼雜湊值與鹽、TOTP 金鑰（AES-GCM 加密）、備用碼雜湊值、Passkey 公鑰 | 註冊、驗證、兩步驟驗證、憑證復原 | Cloudflare D1；密碼 PBKDF2（100,000 次疊代加鹽）、TOTP 靜態加密 | 保存至帳號終止；實體刪除時即刻清除 |
| 網路與裝置資料 | 註冊 IP、最近登入 IP、作業系統、瀏覽器 User-Agent、裝置類型 | 安全稽核、異常登入識別、限流 | Cloudflare D1；限管理員稽核存取 | 保存至帳號實體刪除 |
| 工作階段狀態 | JWT 權杖、RBAC 角色識別、選定信箱 | 邊緣閘道授權、請求路由 | Cloudflare KV；最長有效期 30 日 | 登出即撤銷；30 日未活動自然過期 |
| 通訊資料 | 寄件人與收件人、CC/BCC、主旨、時間戳記、已讀狀態、標籤、星號、內文 | 郵件投遞、對話組織、搜尋 | Cloudflare D1（中繼資料）；依模式以 AES-256-GCM 靜態加密 | 由當事人控制；垃圾桶 7 日實體刪除；用量逾 90% 時對已刪郵件徑行實體刪除 |
| 附件 | 原始檔名、MIME 類型、檔案大小、二進位內容 | 附件傳輸、內嵌顯示、安全下載 | Cloudflare R2／S3 相容儲存；下載採防禦性標頭 | 隨所屬郵件之生命週期；實體刪除時一併清除 |
| 安全與限流紀錄 | 登入失敗計數、人機驗證狀態、滑動視窗請求計數 | 暴力破解防護、濫用防治 | Cloudflare KV；滑動視窗計數器 | 閾值觸發後 12 小時內自動過期重置 |
| 介面偏好 | 語言（6 語言）、明暗模式、通知旗標 | 介面一致性 | 瀏覽器 localStorage，選擇性同步至 D1 | 保留至清除快取或手動重設 |

## 3. 安全維護措施

營運者建立下列安全維護措施並持續改善，涵蓋人員、流程、技術與稽核各層面：

| 安全維護事項 | 本服務之落實 |
| --- | --- |
| 人員與資源配置 | 實例營運者指定管理員，依 RBAC 多級角色劃分權限 |
| 個人資料範圍之界定 | 本文件第 2 節之處理矩陣，明確界定各類資料 |
| 風險評估及管理機制 | 三種郵件模式之加密選擇、失敗鎖定、限流與配額機制；開放原始碼公開受社群檢視 |
| 事故之預防、通報及應變 | 見本文件第 4 節 |
| 蒐集處理利用之內部管理程序 | [隱私權政策](/zh-tw/mail/privacy-policy/)第 5 節之處理活動對應表 |
| 資料安全管理及人員管理 | 密碼學雜湊路由（防越權存取）、預設拒絕（fail-closed）之權限檢查、非白名單參數於閘道剝離 |
| 認知宣導及教育訓練 | 自行部署營運者應自行辦理；本站文件可作為訓練素材 |
| 設備安全管理 | Cloudflare 邊緣設施承擔實體與虛擬設備安全（SOC 2 Type II、ISO/IEC 27001）；金鑰以環境變數注入，不入程式碼庫 |
| 資料安全稽核機制 | 安全日誌（登入 IP、裝置、失敗紀錄）留存並限稽核存取；工作階段得即時撤銷 |
| 使用紀錄、軌跡資料及證據保存 | 登入與安全日誌保存至帳號實體刪除；濫用事件之證據依[可接受使用政策](/zh-tw/mail/acceptable-use/)保存 |
| 安全維護之整體持續改善 | 開放原始碼專案持續演進；重大安全修復隨版本發布並公告 |

技術措施要點：全站 HTTPS/TLS；HTML 郵件經 DOMPurify 於隔離之 Shadow DOM 淨化後呈現（阻斷腳本、內嵌事件與外部匯入）；附件下載強制 `Content-Disposition: attachment` 與 `X-Content-Type-Options: nosniff`；對 Webhook 與外部儲存端點實施 SSRF 防護（阻斷私有網段與雲端 metadata 位址）；郵件 ID 以 HMAC 混淆路由，防止越權列舉。

:::caution[加密之範圍與限制]
本服務「全部／隱私／加密」三種郵件模式之加密，係伺服器端靜態加密：金鑰由實例伺服器之環境變數與使用者識別衍生。此機制防護資料庫檔案遭竊取或快照洩漏之風險，並非端對端加密；掌握伺服器與金鑰之營運者在技術上具備解密能力。需要營運者亦無法讀取之保密強度者，應自行以 GPG 等端對端加密工具先加密郵件內文再行發送。
:::

## 4. 事件應變與通知

營運者知悉個人資料被竊取、竄改、毀損、滅失或洩漏時，採取下列措施：

1. 即時阻斷侵害來源（撤銷工作階段、封鎖來源、輪替金鑰）；
2. 評估影響範圍並留存紀錄（軌跡資料與證據保存）；
3. 依適用法律及主管機關之規定，通知受影響之當事人並向主管機關通報；通知內容包括侵害事實、可能之危害、已採取之應變措施及當事人得採取之自保措施；
4. 就事件原因檢討並補強對應之安全措施（整體持續改善）。

## 5. 受檢之配合

開放原始碼專案本身不營運任何實例；各實例之檢查與監督，由其營運者依其所在地之適用法律接受。託管實例 `mail.epocanvas.com` 於臺灣營運，營運者接受臺灣主管機關依法實施之檢查與稽核，本文件與[隱私權政策](/zh-tw/mail/privacy-policy/)即作為受檢之基礎文件，並依主管機關依法所為之處分配合辦理。

自行部署之營運者，應就其實例獨立履行前述義務，並自行面對其所在地主管機關之稽核；本文件可作為其建立安全維護計畫之範本。
