## 1. 安全功能與已知限制

### 1.1 傳輸與通訊保密

網站及 API 應使用正確配置的 HTTPS/TLS。對外投遞、收件方系統、外部物件儲存及使用者自行轉寄的整段路徑，不能僅憑瀏覽器連線使用 TLS 就保證全部端到端加密。升級後的 HTML 閱讀預設阻擋遠端圖片、遠端 CSS 與主動內容；一般閱讀可經提示僅允許目前郵件圖片，仍有 IP 與開啟追蹤風險。列印維持預設阻擋，Telegram 分享不允許遠端資源。Google Fonts 外連已移除，Turnstile、外部頭像仍可能請求第三方；見[第三方處理者清單](/zh-tw/mail/sub-processors/)。

### 1.2 邊緣處理與除錯

業務邏輯使用 Cloudflare Workers，持久狀態由資料庫與儲存服務保存。郵件解析、翻譯、投遞及備援可能在記憶體中接觸明文；沙箱可重複使用，不能保證每次請求結束即銷毀實體記憶體，亦不能以無自建伺服器推論平台無日誌或快照。

日誌應遮蔽憑證、郵件正文與不必要識別資料。測試優先採合成內容與隔離資源；不得為重現錯誤而把真實郵件、密鑰或資料庫複本上傳公開儲存庫或未核准的 AI／診斷服務。

### 1.3 靜態加密

郵件模式可對主旨及正文套用 AES-256-GCM 伺服器端靜態加密；適用範圍依模式與記錄狀態決定。完整原始 MIME 另按第 1.5 節以伺服器密鑰 AES-256-GCM 加密；附件與中繼資料不自動取得同樣保護。營運者持有密鑰及伺服器權限，技術上可解密；管理介面的模式限制不等於端對端保密。在隱私模式下，移入垃圾桶可將郵件主旨、正文與驗證碼解密保存並納入管理可見範圍，復原後再按模式加密；加密模式關閉的系統級通知／轉寄不涵蓋所有個人配置的外傳。

實例應使用獨立且妥善保管的密鑰，完成初始化並驗證實際加密狀態，規劃輪替與存取權限。原始碼有加密函式，並不證明每筆歷史資料、備份或第三方副本均已加密。

### 1.4 憑證與工作階段

本次核對版本新寫入密碼採 PBKDF2-HMAC-SHA256，每位使用者隨機鹽，預設 210,000 次迭代；可配置參數且仍接受歷史 SHA-256 或較低參數並於驗證時升級。TOTP 密鑰使用 AES-256-GCM；復原碼有雜湊及可重新驗證後顯示的加密原碼副本，通行金鑰存公開憑證資料。雜湊不是不可猜解保證，後續仍應按風險及技術現況評估參數。

TOTP 設定流程將加密後的設定密鑰寫入 D1 的 `auth_security_operation`，有效期為 300 秒；多因素登入的待完成流程也保存在該 D1 資料表中，其 payload 不含輸入密碼。完成第二步只更新 payload，不會延長原有截止時間；到期會阻止後續使用，但不等於紀錄已實體刪除，排程清理可能稍後處理。若停用 TOTP 時仍有有效通行金鑰，`totpEnabled` 仍保持開啟。登入環境清單最多 15 筆、180 日滑動 TTL；IP 多帳號關聯 TTL 為 7,200 秒，可信裝置憑證可保存 60 日且前 30 日可免除部分多因素驗證。

登入失敗限制與工作階段撤銷均有實作；JWT 預設有效期 30 日。工作階段列表的容量判斷有邊界差異，不能宣稱程式嚴格保證最多 10 個同時工作階段。憑證保存於瀏覽器 localStorage 時，仍須防範共用裝置與腳本存取風險。

### 1.5 資料處理矩陣

| --- | --- | --- | --- |
| 帳號與驗證 | D1 帳號、個人欄位、驗證及設定資料；KV 工作階段 | 註銷先停用全部關聯信箱，撤銷工作階段、PAT、可信裝置、待驗證狀態及 OAuth 授權，入站在 AI 前阻擋 | `manual_review` 不等於全清；失敗以 `cleanup_failed` 留存可查狀態，靜態頭像與殘留副本另核對 |

| 稽核、申訴及裁決 | 稽核事件、風險／工單狀態、申訴、通知與授權稽核資料 | 有條件的手動清除一般舊事件；沒有全類別預設 TTL | 見下段的保留條件；逐類設定期限及刪除程序 |

本機草稿資料庫以主信箱命名，包含收件人、主旨、正文、寄件設定及另表保存的附件物件，未見應用層加密。`epo_sessions` 工作階段權杖登記表、目前郵件及 `epomail_recipient_records:*` 收件人紀錄使用同源持久儲存；各分頁身分標記使用 sessionStorage，多帳號的介面路徑不等於瀏覽器儲存或裝置存取隔離。PWA 有自動註冊的 Service Worker，但本次核對未配置郵件的離線快取，也未見瀏覽器 Web Push 訂閱實作；不能據此忽略本機持久儲存。

每日清理分支設定於 UTC 16:00（臺灣次日 00:00），另有每五分鐘的排程；有排程設定不等於每項清理均每五分鐘執行。使用者執行刪除時，若當時用量已超過配額 90%，所選郵件可直接實體刪除，不是僅由背景工作清除既有垃圾桶。

稽核清除端點只接受特定範圍：超過 180 日、屬一般稽核、正常風險且狀態已結案／過期／駁回，並須排除有效封禁引用。這是技術上的清除條件，並非法定最低保存期；其他事件、申訴、裁決、通知及授權紀錄沒有因此自動到期。營運者須補足合法保存規則及可執行清理，不能把「有清除按鈕」描述為所有日誌已按期刪除。

## 2. 營運與開源責任

### 2.1 託管測試實例

個人維護的測試實例以盡合理努力降低風險為維護原則：結合資料敏感性、處理範圍、技術現況與合理實施成本，優先處理可能造成較大損害的缺陷，並明確說明目前措施及限制。必要流程可採用與風險相當的人工核對、紀錄及清理，不無條件承諾企業級備援、專職值班或特定修復時限。遇到尚不能妥善控制的風險，應減少資料、限制功能或暫停相關處理；已知限制及使用者可採取的措施見[隱私權政策](/zh-tw/mail/privacy-policy/)第 1 節。法定安全要求、權利請求與通報期限仍依適用法律辦理。

### 2.2 原始碼作者與部署者

只提供原始碼而不決定特定實例處理目的或方式者，不因此承擔該實例的營運義務。同一作者若另行營運託管實例，應就該營運負責；實際共同決定或受託處理的角色也須依事實判斷，不能以文件先行排除。

### 2.3 規模相當的治理

小型實例可採用一份簡明電子管理紀錄，記載目的與依據、資料及當事人類別、接收者、地區與傳輸保障、保存／刪除和安全措施；依法須保存處理紀錄時，應具備法定欄位並可向有管轄權的機關提供，不能僅憑不足 250 人免除。權利請求可用非公開工單記錄收件日、期限、核驗、處理範圍及完成情況；定期人工複核與清理可以適用，但須確實執行並留下必要紀錄。

歐盟代表、資料保護長與影響評估須各按法定條件判斷，見隱私權政策第 12 節；隱私信箱不自動成為這些法定職務。無須僅因開源或非營利測試而成立公司、僱用專職團隊、購買保險或取得 ISO 認證，也不能以缺少預算延長法定期限。測試資源即使僅存合成郵件，也應核對真實帳號、存取日誌及外部請求的處理。

### 2.4 對外開放前的確認

營運者身分與地址、實際第三方與所在地、合法處理依據、日誌及備份保存、完整刪除與請求追蹤仍須落實。程式在缺少營運者名稱、國家、聯絡信箱、條款版本及條款／隱私 URL 時關閉新註冊，既有登入仍可用；註冊的條款選框不預選，接受紀錄包含版本、時間、語言及 URL，不額外蒐集 IP 作為接受證據。隱私權政策是另行告知，不是概括處理同意；欄位齊全或勾選不證明主體、契約或合規已核實。未具依據或保障的流須停用，見[隱私權政策](/zh-tw/mail/privacy-policy/)第 2、8 節與[第三方處理者清單](/zh-tw/mail/sub-processors/)第 7 節。

## 3. 權利、刪除與事故

### 3.1 匯出與補充請求

自助 JSON 匯出包含部分個人資料、未標記刪除的郵件映射與自訂標籤，不含所有收件欄位、附件二進位內容、原始郵件、全部信箱別名或管理稽核資料。單封 .eml 不等於保存的完整原始 MIME，亦不保證等同資料庫全部個人資料。機器可讀匯出不會單獨完成所有查閱與可攜義務。

未包含但依法得請求的資料，由人工管道核實並補充；不得以功能沒有提供為由拒絕。回覆期限、核驗、費用與申訴依[隱私權政策](/zh-tw/mail/privacy-policy/)第 9 節。

### 3.2 刪除程序

升級後的註銷先在 D1 停用使用者全部關聯信箱，再撤銷工作階段、PAT、可信裝置、待驗證狀態與 OAuth 授權；入站在 AI 處理前拒絕。公開端點對停用或刪除的使用者／信箱回傳 404；Telegram 閱讀及附件每次檢查使用者、信箱、郵件的狀態及版本。停用或變更個人通知會撤銷舊閱讀連結，資料設定另可明確撤銷全部連結；這不刪除聊天訊息或已下載副本。刪除使用者紀錄前已接入原始 MIME 清理，失敗保留定位資訊供重試。註銷回傳 `manual_review` 仍須人工核對原文、claim 及其他殘留，不是全量清除；清理失敗以 `cleanup_failed` 留存可查狀態，不承諾 90 日全清。原靜態頭像 URL 的檔案不會隨軟刪除實體刪除。

一般登出僅撤銷目前工作階段並清除目前郵件、收件人快取及目前帳號工作階段，保留草稿、其他帳號及不屬於本次撤銷的憑證，不是全工作階段或全閱讀連結撤銷。共用裝置可在資料設定明確確認清除本站全部本機帳號、草稿附件、可信狀態與快取；被阻擋或失敗會回報，不得忽略結果。裝置清除與伺服器註銷、全量刪除須分別核對。

附件自備外部儲存的刪除保留原後端定位與必要配置，直至其刪除佇列中的 pending／failed 項處理完成，再安全移除設定。原始 MIME 的獨立到期清理見第 1.5 節，不使用附件佇列。缺少原配置時標記失敗，不轉用預設儲存桶刪除；營運者須核對重試及每個物件的結果，不能把已排入佇列當作已刪除。

刪除請求應建立可追蹤紀錄，逐一核對帳號、別名、郵件、物件、驗證與授權、稽核及備援系統；依法須保存者記錄依據、隔離用途並告知可提供的理由及期限。未確認完成前不向使用者發出「全部徹底刪除」的回覆。請求處理不得因內部尚未自動化而超過法定期限。

### 3.3 最小化與使用者選擇

程式的自動提取、翻譯、OCR 伺服器門檻預設 false；目前不提供公共翻譯備援。自動提取還須 `aiCode`、使用者 `aiVerificationCode` 明確 true 與告知確認。開啟翻譯面板或換語言不傳送內容，須確認目前告知 URL；OCR 缺省 false，僅本次選擇與伺服器許可均通過才處理。MyMemory／Google 公共備援已從全部路徑移除，後端拒絕啟用值 true、介面選項停用；舊實例須升級，不能只依賴原開關。實際接收實體、契約、保存及跨境保障仍須揭露；確認不是 GDPR 全套證明。公開資料後端分別執行統計／趨勢／來源選項並對停用、刪除使用者／信箱回 404，但原靜態頭像不隨軟刪除清除。升級後的個人 Telegram 強制執行通知範圍、預覽及驗證碼複製控制：`all`／`important` 模式即使關閉預覽，通知標題仍採用主旨（無主旨時用通用標題，最多 200 字元）；`notifyCodeOnly` 僅在非 `privacy` 模式且已有不超過 256 字元驗證碼時新增複製按鈕；`includePreview` 明確為 true 才附最多 400 字元摘要及配置可用時的閱讀連結；`privacy` 模式僅發通用提示。閱讀及附件每次校驗狀態與版本，含預覽關閉情形。轉寄規則無法使用時停止，不回退全部；保存的 `keepCopy` 規範化為 true，啟用轉寄時的 false 會被拒絕，停用配置也寫入 true，原件保留。具體欄位與選擇見[通知與轉寄指南](/zh-tw/mail/notify/)，這些程式機制不代表正式環境驗證完成。

### 3.4 事故應變

發現事故後應控制影響、保全必要證據、判斷涉及資料與風險並記錄決策。GDPR 的監管通報以風險條件為前提，在可行情況下於知悉後 72 小時內辦理；高度風險時依法無不當遲延通知當事人。完整規則見[隱私權政策](/zh-tw/mail/privacy-policy/)第 10 節，不能一律以公開漏洞公告代替個別通知。

安全問題可私下寄至 `announcement@epocanvas.com`，隱私與權利請求寄至 `privacy@epocanvas.com`；公開修補說明應避免包含可識別使用者的事件細節或尚可利用的憑證。
