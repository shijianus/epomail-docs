## 🎯 核心保留准则：存储限制与合规性

EpoMail 严格恪守 **GDPR 第 5 条第 1 款 (e) 项的“存储限制原则 (Storage Limitation)”**：个人数据的保存形式应确保识别数据主体的时间**不超过实现数据处理目的所必需的期限**。

本准则详尽公开系统内各类数据的预设生命周期、自动轮转策略与物理硬删除（Hard Delete）流程。

---

## 📊 数据类型与保留周期对照表

| 数据类型类别 | 典型数据内容 | 预设保留期限 | 生命周期终止触发机制 |
| :--- | :--- | :--- | :--- |
| **活跃邮件数据** | 正常收件箱、发件箱、草稿箱中的邮件正文与附件 | **永久保留**（直到用户主动删除或账号注销） | 用户主动点击删除 |
| **回收站邮件** | 用户移入「回收站 (Trash)」的已删除邮件 | **30 个自然日** | 系统定时 Cron 任务自动物理清理，或用户手动点击「清空回收站」立即物理清除 |
| **登录与审计日志** | 登录成功/失败记录、IP、时间戳、权限变更流水 | **90 个自然日** | 滚动覆盖，超期日志自动逐条清理以释放空间 |
| **临时缓存与限流计数** | 密码尝试计数器、短期 Token 状态 | **15 分钟 - 24 小时** | Cloudflare KV TTL 机制自动过期销毁 |
| **已注销用户数据** | 注销账号名下的所有邮箱、邮件、联系人与凭据 | **7 天防误触冷静期** | 冷静期满后立即启动不可逆的全库物理级清空 |

## 🗑️ 物理彻底删除 (Hard Delete) 的技术兑现

与很多商业系统仅将数据标记为 `is_deleted = 1`（逻辑软删除、数据仍暗中保留在库中供大数据分析）不同，EpoMail 采用真正的**物理硬删除技术流程**：

```
用户点击「彻底删除」/ 回收站 30 天到期
                   │
                   ▼
      [启动 D1 事务级硬删除流程]
                   │
                   ├── 1. 从 email_attachments 表检索该邮件名下所有附件 R2 Key
                   ├── 2. 调用 env.r2.delete(attachmentKey) 物理清除对象存储
                   ├── 3. 调用 env.r2.delete(rawEmlKey) 物理清除原始报文文件
                   ├── 4. 执行 SQL: DELETE FROM email_bodies WHERE id = ?
                   └── 5. 执行 SQL: DELETE FROM emails WHERE id = ?
                   │
                   ▼
       物理清空完成 (物理零残留，不可逆)
```

1. **不可撤销性**：一旦通过硬删除接口执行清除，该邮件正文及附件二进制块将从 Cloudflare 全球集群中物理释放，任何超级管理员均无法技术恢复；
2. **零残留保障**：附件文件在 R2 存储桶中直接被物理 Purge，绝不存在脱离索引的孤儿残留文件。

## 💾 冷备份介质中的滞后清除窗口说明

为了防范意外灾难，自托管站长通常会按周或按月执行离线 SQL 导出。

若某一邮件在第 1 天被导出到离线冷备份中，随后在第 2 天被用户物理彻底删除：
- 该邮件在线上生产系统中已立即物理毁灭；
- 离线冷备份中的历史镜像将随着备份策略的滚动保留周期（通常为 30 至 60 天），在下一次轮转覆盖时**自动被彻底抹除**。在此期间，任何离线备份数据均受到物理加密隔离保护。
